# 架构与代码定位

## 请求路径

浏览器经 Caddy/Next.js 页面调用 Route Handler；Route Handler 通过 `lib/auth.ts` 校验会话、角色和同源请求，再用 `db/index.ts` 的 PostgreSQL 连接与 `db/schema.ts` 的 Drizzle 模型读写数据。成功的主业务写操作返回新的 `snapshot()`，前端替换当前快照。文件通过鉴权路由读取，不直接公开上传目录。

## 模块地图

- `app/page.tsx`：登录后的单页工作台；管理员和采购员视图、订单录入/筛选、库存、成员、结款和看板事项均在此组装。改 UI 时同时检查相关 CSS：`app/globals.css`、`app/workspace-ui.css`、`app/touch-forms.css`。
- 订单列表的筛选折叠仅是前端呈现状态：管理员的日期、结款状态和时间排序在默认收起的“更多筛选”中；采购员的结款状态同样默认收起。收起时已选条件继续生效，并在折叠按钮上显示摘要；管理员的“清除全部筛选”仍会重置这些条件。
- 管理员和采购员的订单列表筛选、排序及页码由工作台 `Home` 持有：从列表进入编辑页后，无论取消还是保存返回，均保留原有查看条件；带图保存时重新加载快照也不清空它们。批量勾选和确认弹窗仍属于列表组件的临时状态，离开列表后重置。重新加载整个网页会初始化查看条件。
- `snapshot()` 不再把管理员/采购员订单截断为 500/300 笔：列表先对角色可见的全部订单筛选、搜索与排序，再按每页 50 笔展示；筛选结果不超过 50 笔时不显示分页。管理员默认仍看近 30 天，可在日期筛选选择“全部时间”查找更早的订单。分页后勾选、批量动作及未勾选时的 Excel/文案导出仅作用于当前页；标题汇总仍针对全部筛选结果。当前千单规模沿用完整快照，若订单量显著增长，应把列表筛选、分页和看板汇总迁至数据库，避免每次写操作都返回全量订单。
- `app/api/app/route.ts`：`GET` 返回角色化快照；`POST` 以 `action` 分派核心业务。这里承担状态校验、事务、库存变动和审计，是业务改动的首要入口。
- `app/api/auth/**`、`lib/auth.ts`：注册申请、登录/退出、JWT Cookie、角色检查与错误映射。
- `app/api/order-images/route.ts`、`app/api/settlements/proof/route.ts`、`app/api/files/[id]/route.ts`、`lib/file-storage.ts`：订单图、结款凭证及其鉴权读取。
- `lib/courier.ts`：运单号归一化与反查，以及订单详情「物流轨迹」跳转快递100 的地址 `courierTrackingUrl`。没有服务端物流接口，也不需要物流凭证。
- `app/api/orders/recognize/route.ts`、`app/api/receipt/ocr/route.ts`、`app/api/settlements/recognize/route.ts`、`lib/vision.ts`：截图/面单/结款识别。订单识图先保留模型提取的原始商品字段，再返回商品知识库匹配建议；录单界面只对依据充分的唯一候选补全名称/货号，其他情况显示候选或沿用原值。订单识图的模型调用超时返回明确的 504 提示；商品知识库读取或匹配失败只记录日志并提示人工核对，不丢弃已识别字段。识别结果需人工核对，不能直接视为真实订单。
- `product_knowledge`（`db/schema.ts`）、商品资料匹配逻辑、`app/api/product-knowledge/route.ts`：保存标准名称、货号、别名、来源类型和来源订单；管理员可维护，审核通过的订单可供积累。历史回填和描述性规格货号仅作为候选；新审核订单中明显是货号编码的资料及管理员手工确认资料，在高可信匹配时才可自动补全。管理员编辑会将来源标为 `manual`。知识库不存储可迁移到新订单的价格、尺码、数量或物流。
- `app/api/settlements/route.ts`：结款相关独立入口；修改结款时还要核对主业务路由中的 `settle-order`、`batch-settle`、`update-settlement-amount`。
- `app/api/export/route.ts`、`app/api/integrations/dewu/sync/route.ts`：管理员导出与可选外部同步。导出接口的 `GET` 保留完整字段 CSV，并对可能被表格软件当作公式的文本字段加防护前缀；`POST` 接收最多 500 个订单 ID，并生成当前筛选或勾选订单的 Excel 明细。
- `lib/order-copy.ts`：订单列表「导出文案」的纯函数（时间头、按货号+商品名+尺码合并件数、合计），范围与 Excel 导出相同，在浏览器端生成并复制，不经过服务端。
- `db/schema.ts`、`drizzle/*.sql`、`scripts/bootstrap.mjs`：类型模型、实际迁移、启动迁移器。迁移器用 `_junjun_migrations` 记录已执行文件；不要改写生产已执行 SQL。
- `tests/*.mjs`：结构、识图归一化、时间、物流匹配、部署镜像及订单唯一性集成测试。

## API 阅读方式

主业务 `POST /api/app` 的真实动作名以 `if(action===...)` 为准，目前涵盖：订单创建/重提/编辑/批量删除，审核/驳回，入库/退回在途，逐商品/批量发货，单笔/批量结款及金额更新，成员创建/审批/角色/启停/删除/重置密码，以及看板事项创建/编辑/完成。商品资料管理通过独立接口实现。不要只看旧版 API 列表；新增动作时需要同步权限、输入校验、事务、审计、前端调用和测试。

`snapshot()` 会按角色裁剪订单字段和可见范围；采购员不应从接口收到管理员专有信息。前端不应独立推导最终数据库状态。

## 运行拓扑

- 本地：`npm ci`、本地 PostgreSQL、`.env.local`、`npm run db:bootstrap`、`npm run dev`，参见 [README](../../README.md)。
- 生产：Docker Compose 的 PostgreSQL + Next.js 应用 + 反向代理；数据库和上传文件分别持久化。部署脚本、仓库切换和回滚细节见 [CI/CD 说明](../../deploy/ci/README.md)。
- 不要把 `.env`、密钥、真实生产数据或数据库备份提交到 Git。
