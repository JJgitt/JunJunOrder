# 已发货订单回滚

## 入口和适用范围

管理员打开已全部发货订单的详情，选择“回滚到在途（未结款）”，核对提示、选填原因并二次确认。采购员不显示入口，服务端也拒绝采购员操作。部分发货和未发货订单不适用，普通“撤销入库”仍保留原来的限制。

这是系统记录纠错，不是真实退款或拦截快递。管理员必须先确认实物和资金如何处理；回滚后系统将把商品视为未入库在途，采购员可按既有在途权限查看和编辑。

## 状态与数据

- 订单变为 `在途`、`settled=false`，清空入库时间、库位、结款金额/时间/人员。
- 全部商品清空发货时间、物流、运单号、二级平台/单号及预估售价；商品名称、货号、尺码、数量、采购金额与采购物流保持不变。
- 保留采购人、审核信息、订单号、录入时间及所有普通订单图片。
- 成功回滚同时将 `purchase_orders.is_returned` 设为 `true`。管理员订单列表和详情在当前状态旁展示独立“回流”徽标；这是永久历史标记，后续编辑、入库、结款或再次发货都不清除，也不改变当前状态、筛选或金额统计。采购员接口不返回 `isReturned`，界面不展示，保持其不能查阅发货信息的权限边界。
- 原结款截图用途从 `settlement` 改为 `settlement_archived`，保留文件和元数据，当前订单快照不返回归档图。后续再次结款时，旧凭证不会作为新结款截图；鉴权文件接口仅允许管理员读取归档图。
- 自动看板销售额与估算利润按回滚后的商品状态重新计算；独立的月度人工毛利记账本不受影响。

全部商品已发货时，本单对在库数量的净贡献已经为零，因此回滚不增加或减少库存汇总。对每个已发货批次追加两条 `adjust` 补偿流水：正数撤销原发货、负数撤销原入库，保留全部历史流水，再移除本单当前库存批次。不根据货号/尺码批量删除，不能影响其他订单的同款商品。批次缺失或与商品信息不一致时拒绝，避免掩盖数据异常。回滚后可以重新入库、结款和发货。

## 事务和审计

`POST /api/app`，`action="rollback-shipped-order"`，参数为 `orderId` 和选填 `reason`（最多 500 字）。仅接受数据库已入库或兼容历史已发货状态、商品非空且全已发货的订单。缺少参数返回 400，不存在返回 404，当前状态或批次不满足条件返回 409。

在同一事务内按订单→商品→批次→当前结款图加锁，保存原订单、商品物流/售价、批次和结款凭证信息及原因的 `rollback_shipped_order` 审计，再与补偿流水、字段更新和凭证归档一起提交。审计失败同样回滚；重复请求只能成功一次。物流编辑也先锁订单再锁商品，在锁内检查仍已发货，避免陈旧编辑请求在回滚后重写物流。

迁移 `0017_archive_settlement_proofs.sql` 仅扩展 `order_images.kind` 的允许值并更新中文注释，不改旧图片用途。旧版快照只组装 `order` / `settlement` 图片，保持兼容。

迁移 `0018_returned_order_flag.sql` 新增非空布尔列 `is_returned`（默认 `false`），并根据 `purchase_order` 类型的 `rollback_shipped_order` 审计为已回滚的历史订单补标，不修改订单状态和更新时间。普通“撤销入库”不标记为回流；多个回滚审计也只对应同一条订单标记。新回滚与该标记、库存补偿和审计同事务保存，失败不会留下回流标记。`isReturned` 仅由服务端生成，不提供独立手工勾选或清除入口。

## 测试和上线验收

后端、UI 和隔离 PostgreSQL 测试覆盖权限、确认与失败重试、全发货/部分发货、未结款/已结款、同款多商品、重复回滚、并发、审计失败、旧图归档及回滚后重新入库发货。生产只检查迁移、接口及服务健康，不拿真实订单试回滚。
