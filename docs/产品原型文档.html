1. 产品概述

业务背景：团队从京东、拼多多、淘宝等多渠道平台低价采购商品（以鞋类、潮品为主），收到货后入库，再通过得物等二级平台加价卖出赚取差价。当前流程分散在微信沟通 + Excel 记账中，订单流转状态不透明，采购与发货环节容易出现「谁买的、到没到货、发没发」的信息断层。

产品定位：一款轻量级 H5 小工具，贯穿「采购下单 → 到货入库 → 平台售出 → 出库发货 → 利润核算」全链路，分采购员前台与管理员后台两端。

1.1 产品目标

  • 采购员：在电商平台下单后 10 秒内完成订单上报，无需沟通任何人。
  • 管理员：随时随地掌握所有在途/在库/待发订单，入库、发货一键操作。
  • 账目清晰：自动汇总每单的采购成本，为后续利润核算打基础。

1.2 端与角色划分

端使用者核心场景入口
采购员前台 负责在京东/拼多多下单的采购人员 下单后上传订单（手动录入 / 截图）；查看自己上传的订单状态 H5，账号密码登录
管理员后台 老板 / 负责人 订单查询与审核；📷 拍照识别快递单收货入库；发货标记；库存查看；采购员管理；数据看板 同一 H5（登录角色自动进入对应端）
💡 一码两端：不做独立 App。同一个 H5 链接，登录时根据角色自动分流 —— 采购员进入前台界面，管理员进入管理后台。后续如需小程序可平移复用接口。

3.2 逆向流程

  • 审核驳回：信息错误 → 管理员驳回并注明原因 → 采购员收到通知修改重新提交。
  • 采购退货：京东/拼多多到手价不划算或商品瑕疵 → 管理员标记「采购退货」，记入损耗。
  • 二级平台退回：得物质检不通过退回 → 状态回退到「已入库」，可二次上架或转渠道处理。
  • 撤销入库：入库操作错误（如错认包裹、库位填错）→ 管理员在订单详情点「退回在途」，状态回退到「在途」，入库时增加的库存同步扣回，可重新入库。订单内只要有一件商品已发货就不允许退回。

3.3 收货入库 · 拍照识别流程（核心新增）

包裹到货后，管理员不再需要翻 Excel 或问人「这单是谁的」，直接拍照识别面单上的物流单号，系统自动反查关联的货品与采购订单：

确认入库填库位完成收货
状态 在途 → 已入库
  • 匹配成功：展示该快递单关联的货品名称、货号/尺码、采购渠道、采购订单号、采购员、金额 → 管理员核对实物后确认入库。
  • 未匹配：提示可能原因（采购员未填快递单号 / 单号识别有误），提供 3 条补救路径 —— ① 手动输入单号重查；② 重新拍照；③ 手动绑定到某笔在途订单。
  • 同一单号重复入库：系统拦截，防止一货多收。
⚠️ 前置条件：该功能依赖采购员上传订单时填写快递单号。因此「快递单号」为必填项，OCR 识别才有匹配依据；「平台订单号」为选填，填写后同一平台内不允许重复。
⚠️ 关键设计点：一单到底。采购订单（上游）与二级平台售出（下游）通过 SKU 关联而非一对一绑定：一次采购的商品可能分多次在二级平台卖出，也可能一个二级平台订单由多个采购单凑齐。因此库存表以「SKU + 尺码」为粒度，采购入库增加库存，发货扣减库存。

8. 数据模型设计

基于现有 Drizzle + PostgreSQL 技术栈，核心表如下（采购单为"订单头 + 商品行"结构，一单可含多商品）：

表字段（关键字段 / 类型）说明
users 用户 id、phone、name、password_hash、role(purchaser/admin)、status(启用/停用)、created_at 登录与角色分流
purchase_orders 采购单（订单头） id、platform(京东/拼多多/淘宝/唯品会/抖音…)、platform_order_no(选填，同平台非空唯一)、courier_company(快递公司)、courier_no(快递单号，必填)、status(待审核/在途/已入库/已驳回)、reject_reason、purchaser_id、auditor_id、入库时间、库位、created_at、updated_at 订单头，承载整单共享信息与入库前状态机；按 platform_order_no + platform 唯一约束防重复上传；courier_no 建索引 —— 仓库拍照 OCR 反查的唯一依据；入库时间非空即表示已收货
order_items 采购单商品行 id、order_id(所属采购单)、title、sku(货号)、size、qty、amount(该商品实付)、二级平台、二级平台单号、售价、发货物流公司、发货快递单号、shipped_at、created_at、updated_at 一单多商品，每行独立发货；入库后订单展示状态由商品行推导：全部发货=已发货，否则=待发货
order_images 订单截图 id、purchase_order_id、url、sort 每单 ≤3 张，存 R2
inventory 库存 id、sku、size、count、locations(库位集合)、updated_at SKU+尺码粒度；入库 +qty，发货 −qty
order_logs 流转日志 id、purchase_order_id、from_status、to_status、operator_id、note、created_at 支撑详情页时间线与审计
✅ 与现有工程的衔接：现有 db/schema.ts 为空、`examples/d1` 提供了完整接入范式。落地时先建上表 → `npm run db:generate` 生成迁移 → 在 `.openai/hosting.json` 启用 D1 → 按 `examples/d1/app/api/notes/route.ts` 的模式写 `/api/orders` 等 REST 接口即可。

10. 验收标准（v1.0 核心用例）

  1. 采购员登录 → 上传一笔京东订单（含快递单号）→ 管理员看板「待审核」+1，且收到列表刷新。
  2. 管理员审核驳回（填原因）→ 采购员首页出现驳回置顶提醒，可修改重提。
  3. 管理员对快递面单拍照 → 系统识别出快递单号 → 反查展示关联货品与采购订单号（渠道/采购员/金额）→ 填库位确认入库 → 状态变「已入库」、库存 +1、采购员端同步可见。
  4. 识别出的单号在系统中无匹配 → 提示原因（采购员未填单号/识别有误），支持手动改单号重查、从尾号模糊匹配列表绑定、标记异常包裹三种补救路径。
  5. 同一快递单号重复入库 → 系统拦截，提示已收货。
  6. 管理员填写发货物流公司和运单号（二级平台单号、预估售价选填）→ 库存 −1，状态「已发货」；修改已发货订单的预估售价及物流不得重复扣库存。
  7. 同一平台单号重复上传 → 系统拦截并提示已存在。
  8. 看板数据与订单列表实际数据一致（今日入库/待发货数量核对无误）。
